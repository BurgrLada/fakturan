# MCP: odchylky od spec a plánu

Co pluginy Better Auth (`@better-auth/mcp`, `@better-auth/oauth-provider`, `@better-auth/cimd` 1.7.14) dělají jinak, než spec nebo plán předpokládá (MCP-040). Povinné body MCP-040 (PKCE, audience, registrace pro Claude Code) plugin splňuje, ověřuje to `tests/backend/mcp-auth-server.test.ts`.

## Task 1

- **Rozsah `offline_access` navíc.** Plugin vydá obnovovací token jen tehdy, když klient požádá o `offline_access`. Bez toho by asistent musel projít přihlášením každých 15 minut, což odporuje MCP-007. `scopes`, `clientRegistrationDefaultScopes` i `clientRegistrationAllowedScopes` jsou proto `["fakturan", "offline_access"]`. Metadata chráněného zdroje (`/.well-known/oauth-protected-resource/api/mcp`) dál nabízejí jen `fakturan`, protože plugin rozsahy autorizačního serveru z metadat zdroje vynechává. Metadata autorizačního serveru nabízejí oba. `MCP_SCOPE` zůstává `"fakturan"`. Důsledek: klient, který si rozsah vezme z metadat chráněného zdroje, požádá jen o `fakturan` a obnovovací token nedostane. Řeší to Task 5 (výzva `WWW-Authenticate`) a Task 8 (ověření skutečným klientem).
- **`clientRegistrationDefaultApplicationType: "infer"` navíc.** Výchozí typ `web` odmítne zpětnou smyčku `http://127.0.0.1:…/callback`, kterou Claude Code registruje bez `application_type`. `infer` z takové adresy odvodí klienta typu `native`. Webové klienty dál platí pravidla pro `web`.
- **`grantTypes: ["authorization_code", "refresh_token"]` navíc.** Výchozí seznam obsahuje i `client_credentials`. Ten by umožnil token bez přihlášeného uživatele, a ten MCP nepotřebuje.
- **JWT relace pluginu `jwt` jsou vypnuté.** Cesta `/token` je v `disabledPaths` a `jwt({ disableSettingJwtHeader: true })` vypíná hlavičku `set-auth-jwt`, kterou by jinak každé `/get-session` přihlášeného uživatele vracelo s JWT podepsaným stejnými klíči jako přístupové tokeny MCP (`sub` = id uživatele). Klíči plugin podepisuje jen přístupové tokeny z `/oauth2/token`. Klíče na `/api/auth/jwks` zůstávají. Ověřuje to test `[MCP-007] autorizace s PKCE …, relace JWT nevydá`.
- **Metadata v kořeni domény.** Router Better Auth vrátí 404 na každou cestu mimo `/api/auth` dřív, než se spustí hook `onRequest` pluginu. Metadata v kořeni proto obsluhují trasy Next `src/app/.well-known/oauth-authorization-server/[[...issuer]]` a `src/app/.well-known/oauth-protected-resource/[[...path]]`. Předají požadavek přímo hooku `onRequest` pluginu `oauth-provider` (`src/server/mcp/well-known.ts`), takže dokumenty skládá plugin sám. Helper `oauthProviderResourceClient().getProtectedResourceMetadata` použitý není, protože jako `authorization_servers` uvádí `BETTER_AUTH_URL` bez `/api/auth`, a to se neshoduje s vydavatelem tokenů. Pod `/api/auth/.well-known/oauth-authorization-server` metadata obsluhuje přímo `[...all]`.
- **`/.well-known/openid-configuration` se nepublikuje.** Mezi rozsahy chybí `openid`, takže server není poskytovatel OIDC a plugin tento dokument nevydává. Klienti MCP hledají nejdřív `oauth-authorization-server`.
- **Limit registrace.** Vestavěný limiter Better Auth je v instanci vypnutý (`rateLimit.enabled: false`), takže výchozí limity pluginu neplatí. Registraci `/oauth2/register` hlídá `oauthRegisterIp` (10 za hodinu podle IP) ve stávajícím `rate-limits.ts`.
- **CIMD je zapojený, ale neověřený.** `cimd({ fetchClientMetadataResource, metadataProfile: "mcp-2026-07-28" })` používá transport z `@better-auth/cimd/node`. Ten odmítá adresy z privátních rozsahů a zpětnou smyčku, takže lokálně ani offline ho otestovat nejde. Testy pokrývají jen DCR.

## Task 2

- **Pokračování přihlášení zajišťuje klientský plugin.** `authClient` má `oauthProviderClient()` z `@better-auth/oauth-provider/client`. Na stránce s podepsaným dotazem (`sig`) přidá ke každému POST pole `oauth_query`. Server po vzniku relace sám spustí `/oauth2/authorize` a vrátí `{ redirect: true, url }` na souhlas. Přihlašovací formulář pak místo `router.push("/")` přejde na `url`. U sociálního přihlášení plugin uloží dotaz do stavu OAuth a návrat z poskytovatele přesměruje rovnou na souhlas. Stránku `/prihlaseni` nebylo třeba měnit, jen `login-form.tsx` a `auth-client.ts`.
- **Souhlasová stránka bez relace nepoužívá `requireSession`.** Ta by přesměrovala na `/prihlaseni` bez dotazu a rozpracovaná autorizace by se ztratila. Stránka proto při platném podpisu přesměruje na `/prihlaseni?<podepsaný dotaz>` a po přihlášení se vrátí zpět, jinak na prosté `/prihlaseni`.
- **Odmítnuté sociální přihlášení ukončí autorizaci.** Cizí e-mail skončí na `SOCIAL_REJECTED_PATH` (`/prihlaseni?chyba=pozvanka`) stejně jako ve webu (MCP-004). Podepsaný dotaz se tím ztratí a asistent musí připojení spustit znovu.

## Task 3

- **MCP-006 stojí na kroku `postLogin` pluginu.** Volba `postLogin` (`page`, `shouldRedirect`, `consentReferenceId`) běží uvnitř každé autorizace, i té, kterou plugin sám spustí po přihlášení. Při vypnutém přístupu vrátí `shouldRedirect` hodnotu `true` a plugin pošle prohlížeč na `/pristup-asistenta`, která místo souhlasu ukáže vysvětlení s odkazem do Nastavení. Kód se nevydá ani klientovi se zapamatovaným souhlasem. `consentReferenceId` vrací `undefined`, takže souhlasy se ukládají bez reference jako dosud.
- **Co `postLogin` nepokryje, hlídá vlastní `before` hook** (`src/server/mcp/access-guard.ts`): `POST /oauth2/consent` s `accept: true` a `/oauth2/continue` (dotaz na souhlas nese značku pluginu `ba_pl`, se kterou se `shouldRedirect` přeskočí) vrátí `403 MCP_DISABLED`. Výměna kódu na `/oauth2/token` vrátí `invalid_grant`, pokud majitel kódu mezitím přístup vypnul. Majitele kódu hook najde stejně jako plugin: SHA-256 kódu v base64url (`storeTokens: "hashed"`, výchozí). Změnu v pluginu zachytí test `[MCP-006]`.
- **Obnovovací token při vypnutém přístupu platí dál.** Vypnutí podle MCP-010 propojení nesmaže. Kdyby `/oauth2/token` odmítl i obnovu, klient by obnovovací token zahodil a po zapnutí by se musel připojit znovu. Volání nástrojů odmítne endpoint MCP sám (MCP-012, Task 5).
- **Opakovaná autorizace se zapamatovaným souhlasem se neaudituje.** `mcp.connected` se zapíše jen po přijatém souhlasu, který skončil kódem pro klienta. Když plugin souhlas přeskočí, jde o obnovu téhož povolení, ne o nové vydání přístupu (MCP-031), a záznam by se opakoval při každém připojení asistenta.
- **„Naposledy použit“ je vlastní sloupec `oauth_consent.last_used_at`.** Plugin takový sloupec nemá. Souhlas při opakovaném povolení jen aktualizuje vybraná pole, takže hodnota přežije.
- **Záloha zůstává ve verzi 2.** `mcp_settings` přibyla do registru jako tabulka verze 2 (`since: 2`) a otisk `columns-v2.json` se doplnil, stejně jako dříve u `mail_look`. Archiv v2 vytvořený před touto změnou má jiný otisk sloupců a obnova ho odmítne. Stejný důsledek měla změna `mail_look`.

## Task 5

- **`offline_access` nabízí výzva `WWW-Authenticate`.** `requireMcpAuth` má volbu `challengeScopes`. Endpoint ji nastaví na `["fakturan", "offline_access"]`, takže odpověď 401 nese `scope="fakturan offline_access"` vedle `resource_metadata=`. Klient podle specifikace MCP bere rozsah nejdřív z této výzvy, a teprve potom ze `scopes_supported` v metadatech chráněného zdroje. Požádá tedy i o `offline_access` a dostane obnovovací token. Metadata chráněného zdroje dál nabízejí jen `fakturan`, protože plugin tento rozsah z nich vynechává záměrně. Vynutí se jen `fakturan` (`requiredScopes`): token bez něj dostane 403 `insufficient_scope`. Jestli se tak chová i skutečný klient, ověří Task 8.
- **Limit volání vrací chybu nástroje, ne HTTP 429.** Limit (60 za minutu na uživatele a klienta, MCP-032) se kontroluje uvnitř obalu nástroje, tedy uvnitř jedné odpovědi JSON-RPC. Překročení proto vrátí `isError` s českou větou „Příliš mnoho volání najednou. Zkuste to znovu za N s.“. První odmítnutí v okně se zapíše do auditu jako `rate_limit.exceeded`, stejně jako u ostatních limitů. Registrace klienta dál vrací 429.
- **Klíče JWKS si endpoint stahuje přes HTTP z vlastní adresy.** `requireMcpAuth` ověřuje token proti `<BETTER_AUTH_URL>/api/auth/jwks` a klíče drží 5 minut v paměti. Server proto musí dosáhnout na svou vlastní veřejnou adresu (u reverzní proxy nebo tunelu to obvykle platí). Když stažení selže, každý požadavek dostane 401.
- **Vstup kontroluje obal, ne SDK.** SDK by argumenty ověřilo podle schématu dřív, než obal zkontroluje přístup, a chybu by vrátilo anglicky. Nástroje se proto registrují se schématem, které se v `tools/list` zobrazí celé, ale argumenty propustí beze změny. Ověří je až `runTool` (Zod s českými hláškami, výčet všech polí). Výstup ověřuje také `runTool`: nesoulad se schématem je chyba Fakturanu, jde do Sentry a uživatel dostane obecnou větu.
- **Trasa staví ověření tokenu při každém požadavku.** `src/app/api/mcp/route.ts` volá `mcpEndpoint(auth, env, request)`. Uvnitř se `requireMcpAuth` a `createMcpHandler` (`legacy: "stateless"`) vytvoří pro každý požadavek, protože `auth` a `env` jsou líné a `next build` je nesmí číst. Metodu `GET` a `DELETE` trasa nemá, Next odpoví 405.
- **„Naposledy použit“ se zapíše jen po úspěšném volání.** Odmítnuté nebo chybné volání `last_used_at` nemění.
